# NO THIRD-PARTY CODE (standing rule from the owner; read this first)

The owner has said this many times and it must never need saying again.

- **Never add third-party code of any kind.** No npm, pip or cargo packages; no vendored or cloned source; no SDKs, CLIs, apps or models; no `npm install <pkg>` or `pip install` to make something work, not even "just to test". Write it with Node built-ins, the Python standard library, and this project's own modules.
- **If a task seems to need third-party code, stop and ask.** Do not pick a library and add it. Do not add a dependency to get past a failing step.
- **The only exceptions are ones the owner named:** web search through an open-source SearXNG instance, and an Ollama model reached over HTTP. Both are services the owner runs; nothing from them is vendored or imported. Everything else needs a fresh yes.
- **No tokenizer.** Text, audio, and images all enter the mesh as the raw bits they are through the Zip Loop. Do not add word or subword tokenizers, outside embeddings, or speech-to-text (no Whisper, Vosk, Wispr Flow or similar).
- **Check before claiming.** Before saying something is or is not third-party, or is or is not in the repo, look at the files. Do not describe code from memory.
- **This rule is enforced, not just written down.** `node scripts/check-no-third-party.mjs` (also `npm run check:third-party`) fails on any package outside `.third-party-allowlist.json`, any lockfile or manifest for another package manager, vendored folders, jars and archives, imports of anything that is not a Node/Python/platform built-in, bundled or minified code, other people's licence or copyright banners, `uses:` actions outside the allow-list, and `npm install <pkg>` / `pip install` / `npx <pkg>` / `git clone` / `git submodule` / `curl | sh` commands. It runs in the git pre-commit and pre-push hooks (`.githooks/`, set up by `npm install`), in CI (`.github/workflows/no-third-party.yml`), in the test suite (`test/core/no-third-party.test.ts`), and as Claude Code hooks (`.claude/settings.json`, `.claude/hooks/block-third-party.mjs`) that stop the assistant before it installs or pastes anything and before it finishes with third-party code left in the repo. Only the owner may edit the guard files or the allow-list (`CODEOWNERS`, and the hook refuses edits to them). If the check fails, remove the third-party code; do not widen the allow-list, add an exemption, or use `--no-verify`. The check cannot see a plain function pasted from a website with no banner, so that part stays on whoever writes the code.
- Already present and not to be added to: `typescript`, `@types/node` and `vitest` as build and test tools. Known leftovers still to be removed: `torch` imports in `model && skills manager/neurolang.py` and the `torch`, `numpy`, `sentencepiece` lines in that folder's `requirements.txt`.

# ENCRYPTED AT REST, FAIL CLOSED (standing rule from the owner; applies to all stored data)

The owner wants a physical-style guarantee: with the device powered off, or with its operating-system security broken, a thief or a virus must get nothing readable, only an error. This is the rule that makes that real.

- **Anything the app keeps on disk is ciphertext.** Memory, learned weights, chat history, the shared mesh, config that holds secrets, logs that can hold user text, caches, exports and backups. Plaintext may exist only in RAM while the owner has unlocked the app, and is wiped when it locks, quits or crashes. A file written in the clear is a bug.
- **The key never sits beside the data.** It is derived from something the owner holds (passphrase through `crypto.scrypt`, and where the platform offers one a hardware-backed key such as TPM, Secure Enclave or the OS keystore) and is never written to disk, config, logs, environment files or the repo. Powered off means locked: no key in RAM, so nothing opens.
- **256-bit symmetric only.** AES-256-GCM (or ChaCha20-Poly1305) with a fresh random nonce per write, scrypt for key derivation, all from Node's built-in `node:crypto` (`interface/encryption.js` is the one place). Never invent a cipher, never reuse a nonce, never use ECB, plain CBC or an unauthenticated mode. 256-bit symmetric keys are the standard answer to quantum attack (Grover halves the strength to roughly 128 bits, still out of reach), so this is the quantum-resistant choice that needs no outside code. Asymmetric key exchange, if ever needed, needs the owner's yes first.
- **Prefer failure that physics causes, not just software.** AES-256 holds because breaking it is computationally hard. That is maths, not a law of nature, and a bug or a stolen unlocked session defeats it. Where the hardware exists, make the device itself refuse, in this order of preference:
  1. **Key held in silicon, never in a file.** TPM, Apple Secure Enclave, Android StrongBox or Keystore, or the OS keystore (Windows DPAPI/CNG, macOS Keychain). The key is sealed to the chip, cannot be read out, is rate-limited by the chip, and the chip wipes it on tamper. Use only the platform's own first-party interface, never a third-party wrapper. A physical copy of the disk then fails because the key is a property of that one chip, not data.
  2. **Key that exists only as a physical property.** Physically unclonable functions (the per-chip variation of silicon) derive a key while powered and hold nothing when off; opening the chip changes the property and destroys the key. Use when the platform exposes one.
  3. **No single holder of the whole key.** Split the key so that fewer than the threshold of shares reveals nothing at all (information-theoretic, true however much computing the attacker has). A one-time pad is the same idea and is only practical for small secrets.
  4. **Quantum key distribution** is the case where physics itself does it: observing the key disturbs it and an unknown quantum state cannot be copied, so an eavesdropper leaves an error. It needs optical hardware this project does not have. If the owner ever supplies such a device, the app talks to it through its own interface; the app never claims it without one.
- **Physics is the target; software-only is a fallback the owner must choose.** The app asks the platform for the strongest tier above (chip-sealed key first). It never drops to a weaker tier silently. If no chip-backed or token-backed key is available, data classed as secret stays locked and the app says why; the owner may explicitly accept the passphrase-only tier for a given device, and that choice is shown on the status page every time. The app can demand and verify hardware, but it cannot create a physical law in code: no commodity device today provides the quantum no-cloning guarantee, so the realistic physical guarantees are a key that lives only in a tamper-wiping chip, and a key that lives on a separate physical token (a security key or USB token) that must be present. Remove the token or the chip and the data is unreadable by construction, not by policy.
- **Provably unbreakable where it can be, honest everywhere else.** The master key and recovery secrets get information-theoretic protection: split into shares so fewer than the threshold reveal nothing, with the shares on separate physical holders (chip, token, paper). That holds against any computer, quantum included. Bulk data uses AES-256-GCM plus a key no attacker can reach, which is strong but not a proof. Real attacks go around the cipher (malware on an unlocked device, keyloggers, app bugs, side channels, coercion), so the design also keeps the app small, locked by default, and the key out of reach.
- **Never write "unhackable", "impossible to hack" or "unbreakable" about the app** in code, docs, the UI or a reply. Say what is protected, against what, and what is not. The target is "no known way in and no way to take the key", never "impossible".
- **Hidden: not just the contents.** File names, folder layout, sizes and timestamps are part of what an attacker learns. Store the vault as uniformly named, padded, encrypted blobs with the index inside the encryption, so what sits on disk says as little as possible about what exists.
- **Cannot be altered unseen, cannot be lost to one accident.** Every blob is authenticated (GCM tag), and the history is a hash chain (each record covers the one before, via `node:crypto` SHA-256), so a changed, removed, reordered or rolled-back record breaks the chain and the app locks with the standard error. Nothing can stop physical destruction of one device, so keep several encrypted copies on separate physical holders and test the restore; a backup that has never been restored does not count. Never claim the data "cannot be destroyed".
- **Built to survive a virus on the device, not just a thief.** Assume malware can run as the owner. So:
  1. **The key cannot be copied out.** Held in a chip or token that does the decrypting inside itself and never hands the key over. Malware can ask it to decrypt, but cannot take the key, and cannot ask silently: secret-class reads need a fresh physical act from the owner (PIN, touch, token press), which software cannot fake.
  2. **Short unlock windows.** Re-lock after idle, on screen lock, on suspend and after each secret-class read. Wipe keys and decrypted buffers from RAM on lock.
  3. **The app checks itself.** At start it hashes its own files against a manifest signed by a key held in the chip or token, not on disk. A changed file means locked with the standard error, never run anyway. Malware that edits the app and the manifest together still fails, because it cannot sign.
  4. **Small attack surface.** No `eval`, no running downloaded code, no loading plugins or models that are not hash-pinned in the signed manifest, no open ports beyond what the owner enabled, network off by default for the vault process, least privilege and a separate process for the vault.
  5. **Notice and stop.** Unexpected reads, bulk reads and repeated failures lock the vault and log the event without secrets.
  Limit stated plainly: a virus with full control of an unlocked device can still see what is on screen and what the owner approves. This design shrinks that, it does not erase it.
- **Top tier: the vault is not on the machine a virus can reach.** The key and the decrypting live on a separate physical device with fixed firmware, no installed apps, no downloaded code and no network (a hardware token, or a small offline box), and the main machine only sends it a request and receives an answer the owner approved on that device's own button or screen. Malware on the main machine has nothing to run on and nothing to read the key from. Even then it can attack the cable or protocol, the device's own bugs, or you (tricking an approval), so this is the strongest real design, not an impossibility. Never write that a virus "cannot" break it.
- **Say which tier is actually active.** The status page and logs report one line: key held by passphrase only, OS keystore, secure chip, or split. Never display a stronger tier than the one running. Software alone can give tier 0 (passphrase plus AES), and the rule must not pretend it is physics. If a stronger tier is not available on a platform, the app says so.
- **Tamper means an error, never a guess.** Every stored blob carries its authentication tag and a format version. If the tag fails, the key is wrong, the file is truncated or a virus changed one byte, the read throws a plain error (`vault: cannot open, locked or altered`) and returns nothing. No partial data, no fallback to an older plaintext copy, no "repair" that guesses, and no detail in the message that helps an attacker. Repeated bad attempts slow down and are logged without the secret.
- **Locked is the default.** On start, on wake, after idle and on any integrity failure the app is locked and serves nothing but the unlock screen. A failed check locks it; it never opens it.
- **Secrets stay out of everything else.** Never in URLs, command lines, error text, telemetry or the clipboard history. Compare secrets with `crypto.timingSafeEqual`. Zero buffers after use where the runtime allows.
- **Be honest about the limits.** Encryption protects data at rest. It does not help while the app is unlocked and a virus already runs as the owner, and it is only as strong as the passphrase. Real quantum key distribution needs special optical hardware and is not something software can provide, so never claim it, "military grade" or "unbreakable". Say exactly what is protected, when, and against what. If a platform cannot do it (the phone shim has no cipher), say so and do not pretend.
- **No weaker path for convenience.** No debug switch, env flag or "skip encryption" option that ships. A test may use a throwaway key, never a disabled cipher.
- **Where it stands today (checked in the files, not from memory).** `interface/encryption.js` has AES-256-GCM and PBKDF2 and is used for the web password hash. Only one memory-export helper (`src/index.ts`, the unused dashboard code) calls `encrypt()`. The app's stored data is not yet encrypted at rest, there is no locked state, and the phone build has no cipher. Closing that gap is the work this rule asks for; until it is done, nobody may describe the app as encrypted at rest.
- **Enforcement to build, not yet present.** A check that fails if code writes user data to disk outside the vault module, and a test that flips a byte in a stored blob and expects the error above. Add them alongside the vault; do not claim the rule is enforced until they exist.

# Docker Dev Environment

## What this is
NeuroClaw — a local-first AI agent. The backend is a Node/TypeScript HTTP server (port 7861). The React/Vite frontend's npm packages have been removed from `package.json`, so the dashboard no longer builds or runs; its source under `src/` (routes, components, features) is still in the repo but unused.

## Running it
```
docker compose -f docker-compose.dev.yml up -d
```
- Single `web` service on `node:22-slim`, repo bind-mounted at `/app`.
- `npm run dev` (scripts/dev.mjs) does: tsc backend build → starts the backend and stays up until it exits. It no longer starts Vite. Port and bind address come from `NEUROCLAW_WEB_PORT` (default 7861) and `NEUROCLAW_WEB_HOST` (default 127.0.0.1).
- The only npm packages left are the build and test tools: `typescript`, `@types/node`, `vitest`.
- `NEUROCLAW_AUTO_UPDATE=0` disables the startup git fetch/pull so it never touches the working tree.
- The compose file runs the backend itself on its one port, 7861 (`NEUROCLAW_WEB_HOST=0.0.0.0`), and publishes that same process on the host as both `127.0.0.1:7861` and `127.0.0.1:3000`, so http://localhost:3000 and http://localhost:7861 are the same real backend: `/` terminal page, `/app` dashboard, `/api/*`. No proxy sits in front, because a proxy would make remote clients look like loopback and bypass the backend's password gate. Because the bind is non-loopback, the backend wants a password: set `NEUROCLAW_WEB_PASSWORD`, or open `/login` and enter the setup code printed in `docker compose -f docker-compose.dev.yml logs web`.

## Verifying it works
- With a password set, `GET http://localhost:3000/` (or `:7861`) and `/api/status` (Basic auth) return 200 through compose; `/login` answers without one.
- `npm run lint:types` typechecks the backend; `npx vitest run` runs the tests.

## Secrets
None required. The app is local-first. No external API keys needed to boot.

## Notes / gotchas
- Backend build uses the repo's `.bin/tsc` symlink → needs `node_modules` installed first (the dev script handles this).
- Python `asi_core/` is standalone (stdlib only, empty requirements.txt) and is NOT part of the web runtime.
- Web search needs a SearXNG instance: `NEUROCLAW_SEARXNG_URL`, default `http://127.0.0.1:8080` (see plugins/searxng.ts).

## Hard rule: no third-party models or code for anything the network itself should do
The user has said this many times, explicitly: do not bring in a third-party model,
library, or service to do work that belongs to NeuroClaw's own neural mesh or Zip
Loop. No Whisper, no cloud STT/TTS APIs, no third-party ML packages, nothing
downloaded or `npm install`ed to replace or sit in front of the network's own
reasoning. This is a standing rule, not a one-time answer to one request.
- Voice-to-text buttons use only the OS's own first-party API (Android
  `SpeechRecognizer`, iOS `SFSpeechRecognizer`/`AVAudioEngine` via `Speech`/
  `AVFoundation`) purely to turn speech into a text string in the input box.
  That string then goes through `brain.send(text)` exactly like typed text —
  through the real bit-level Zip Loop, no tokenizer, nothing short-circuited.
- Before adding any new dependency (npm, pip, Gradle, CocoaPods/SPM) ask
  whether it does cognition/understanding work the mesh should be doing
  instead. If so, don't add it — extend the mesh/Zip Loop/skills instead,
  even if that's slower or more work.
- There is no tokenizer anywhere in this repo (`tokenizer.js` was deleted,
  not disabled) and it must stay that way: text is raw bits through
  the Zip Loop everywhere, always.

# PLATFORMS AND RELEASES (one app, many builds; map in `docs/PLATFORMS.md`)

- **One shared UI.** The home chat (`HTML_TEMPLATE` in `interface/web-server.ts`) and Settings (`interface/platform/settings-page.ts`) are served by the engine and shown by every platform (desktop app window, Chrome extension, phone web views). Change them once. Never add a per-platform copy of a page or a feature.
- **Platform differences live in one table:** `interface/platform/adapters.ts` (what each OS can really do, with reasons) and `interface/platform/feature-contract.ts` (every feature, its files, routes and tests; support per platform is derived). A new feature gets an entry; `node --test "test/platform/*.test.mjs"` fails if the entry points at something that is not there. The parity matrix in `docs/PLATFORMS.md` is generated: `node scripts/build-backend.mjs && node scripts/release/parity-matrix.mjs --write`.
- **Settings and config never use `process.cwd()`.** Use `interface/platform/app-paths.ts` (`configFile`, `dataRoot`): a desktop entry, an installed app and a service all start somewhere unwritable. Saves must report failure, never throw into a request and never claim success.
- **One version:** `package.json`. After changing it run `node scripts/release/version.mjs sync` (or `set 1.2.3`); a test fails on drift. Every artifact name, `build-info.json` and the release manifest carry that version and the source commit.
- **Tests:** `node --test "test/platform/*.test.mjs"` (Node's built-in runner; needs `node scripts/build-backend.mjs` first, and a Chrome/Chromium for the browser tests). The older vitest suite needs `vitest` installed and is not run by CI when it is missing; say so rather than counting it.
- **CI** (`.github/workflows/ci.yml`) rebuilds only what a change affects (`scripts/release/changed-targets.mjs`) and its summary reports real job results. Do not make a skipped or failed build look like a pass. Only `actions/checkout` and `actions/upload-artifact` may be used.
- **Signing credentials are never in the repo.** macOS signing and notarisation, Windows signing, Play and App Store publishing run only when the owner configures repository secrets; without them the artifacts are labelled unsigned.
- **Pre-existing violations this work did not fix** (the owner decides): `package.json` and `package-lock.json` still list the React/Vite/three stack; `src/`, `dist/app`, `dist/assets` and a tracked `node_modules/` contain third-party code; `desktop-app/` is an Electron project (the packaged desktop path no longer uses it); `mobile/android/gradle/wrapper` holds a Gradle wrapper jar; the iOS CI job installs `xcodegen` with Homebrew.
